# Phase 0: Research & Outline\n\n## Decisions & Rationale\n\n**1. PDF Generation**\n- **Decision**: Use `jspdf` and `html2canvas`.\n- **Rationale**: Required by FR-004 and already present in the project's `package.json`. `html2canvas` allows taking a snapshot of the Vue component's DOM and `jspdf` generates the PDF format safely.\n- **Alternatives considered**: `pdfmake` (rejected as it requires building the PDF document from scratch via JS objects rather than using the existing UI layout).\n\n**2. Component Architecture**\n- **Decision**: Refactor `src/components/RoutineGenerator.vue` from a raw HTML document into a proper Vue 3 `<script setup>` component.\n- **Rationale**: The provided `RoutineGenerator.vue` is currently just a raw `<!DOCTYPE html>` file. To work inside the Quasar/Vue ecosystem and be imported in `PatientDetail.vue`, it must use `<template>`, `<script setup>`, and `<style scoped>` with reactive variables.\n- **Alternatives considered**: Using an iframe to load the HTML (rejected as it prevents reactive data binding with the patient's existing records and API).\n\n**3. API Integration for Saving/Retrieving**\n- **Decision**: Persist the generated routine data as JSON strings in the existing home supports endpoint (`/home-supports`), mapping AM steps to `day_routine` and PM steps to `night_routine`.\n- **Rationale**: The `PatientDetail.vue` component already interacts with `/patients/{id}/home-supports`. By serializing the dynamic steps into JSON, we can save complex structures without requiring backend database schema changes.\n- **Alternatives considered**: Creating a new `/routines` endpoint (rejected as it requires backend modifications not specified or currently available).\n
